# Deploying FinFlow AI — Vercel (frontend) + Render (backend)

You'll end up with: frontend on Vercel, backend API + worker on Render (running inline on the free tier), MongoDB on Atlas (you already have a cluster), Redis on Upstash (free tier).

## 0. Push the project to GitHub

Both Vercel and Render deploy from a git repo, not a local folder.

```bash
cd path\to\finflow-ai
git init
git add .
git commit -m "Initial commit"
```

Create a new **empty** repo on github.com (no README/gitignore — you already have one), then:

```bash
git remote add origin https://github.com/<your-username>/finflow-ai.git
git branch -M main
git push -u origin main
```

## 1. Redis — Upstash (free)

Render's own free tier doesn't include Redis, so use [Upstash](https://upstash.com) (free forever tier, works fine with `ioredis`/BullMQ):

1. Sign up, create a Redis database (any region close to where Render deploys).
2. On the database page, copy the **Endpoint** (host), **Port**, and **Password** — you'll paste these into Render in step 3.

## 2. MongoDB — you already have this

You pasted an Atlas connection string earlier — that's your `MONGO_URI`. Two things to check in Atlas before deploying:
- **Network Access** → add `0.0.0.0/0` (allow from anywhere) so Render can reach it, since Render's outbound IPs aren't static on the free tier.
- Since you shared that URI in this chat, rotate the database user's password now (Atlas → Database Access → edit user) and use the new one going forward.

## 3. Backend — Render

1. Go to [render.com](https://render.com) → **New** → **Blueprint**.
2. Connect the GitHub repo you just pushed. Render will detect `render.yaml` at the repo root automatically.
3. It creates one web service, `finflow-backend`, building from the `backend/` folder. Render will prompt you to fill in the env vars marked `sync: false`:
   - `MONGO_URI` — your Atlas connection string
   - `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD` — from Upstash
   - `OPENAI_API_KEY` — yours (rotate the one you pasted earlier, same reasoning as above)
   - `CLIENT_URL` — leave a placeholder for now (e.g. `https://placeholder.vercel.app`); you'll fix this in step 5 once Vercel gives you a real URL
   - SMTP vars — optional, leave blank if you don't need real emails yet (the app logs instead of failing)
4. Deploy. `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` are auto-generated by Render — you don't need to fill those in.
5. Once live, note your backend URL, e.g. `https://finflow-backend.onrender.com`. Check `https://finflow-backend.onrender.com/health` returns `{"success":true,...}`.

`render.yaml` sets `RUN_WORKER_INLINE=true`, so the workflow worker runs inside this same free web service — no separate paid worker service needed. Fine for a demo; revisit if you outgrow it (config for a dedicated worker service is already commented out in `render.yaml`).

**Seed demo data** once deployed: in the Render dashboard, open the service → **Shell** tab, and run:
```bash
npm run seed
```

## 4. Frontend — Vercel

1. Go to [vercel.com](https://vercel.com) → **Add New Project** → import the same GitHub repo.
2. When configuring the project, set **Root Directory** to `frontend`. Vercel auto-detects Vite.
3. Add an environment variable: `VITE_API_URL` = `https://finflow-backend.onrender.com/api` (your Render URL + `/api`).
4. Deploy. You'll get a URL like `https://finflow-ai.vercel.app`.

## 5. Connect them (fix CORS)

Go back to Render → `finflow-backend` → Environment, and set `CLIENT_URL` to your real Vercel URL (`https://finflow-ai.vercel.app`), then trigger a redeploy (Render → Manual Deploy). Without this step, the backend will reject requests from your frontend's origin.

## 6. Test it

Visit your Vercel URL, log in with `admin@finflow.ai` / `Password123!` (from the seed step). If login fails with a network error, double check `VITE_API_URL` on Vercel and `CLIENT_URL` on Render match exactly (including `https://`, no trailing slash mismatch).

## Known limitations of this setup

Render's free tier spins the service down after 15 minutes of inactivity — the first request after idle will be slow (~30s cold start). Generated invoice PDFs are written to local disk (`backend/uploads`), which is **ephemeral** on Render — they'll disappear on redeploy/restart. For real production use, swap `invoicePdfService.ts` to upload to S3/Cloudinary instead of local disk; that's a small, isolated change since the rest of the app just consumes the returned URL.
